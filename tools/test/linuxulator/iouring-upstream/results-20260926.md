# io_uring qualification — September 26, 2026

**The broader compatibility qualification failed.** Fio works in the tested
modes, but the remaining work includes ordinary I/O semantics and a reachable
kernel assertion, in addition to missing advanced backends. This run adds tests,
reproducible workloads, evidence, and corrected documentation; it does not claim
to fix the discovered kernel problems.

The candidate is the September 26 SQPOLL-affinity kernel, SHA-256
`cae50f3dc0615a828226d57f5d21a78eafc5544bbbffc1c7b77a681611d9f984`,
with WITNESS/INVARIANTS. Both VMs use four emulated CPUs. Candidate files are on
ZFS, Linux files on tmpfs; candidate RAM is 1.5 GiB and Linux RAM is 1 GiB.
The selected upstream suite is **70 cases, not the entire liburing suite**.
A passing executable can internally skip unsupported subtests. For example,
Linux's `file-register` skips its huge-file-set subtest. The JSON retains those
messages instead of claiming every subtest ran.

The hard-link case panicked in the first candidate run. A fresh continuation VM
explicitly quarantined it and completed the other 69 cases. The continuation
ended with **four registered files and two wired pages** still accounted for;
this needs process/resource ownership investigation and is not yet proven to be
an unreachable kernel leak. The separate fio and native stress VMs both returned
all five tracked counters to zero and shut down with healthy ZFS pools. Kernel
crashes and resource residue are not excused by successful fio results.

## What needs attention next

1. **Hard-link assertion:** liburing `hardlink` reaches
   `linux_linkat → kern_linkat → namei_emptypath` with `AT_EMPTY_PATH` and
   `WANTPARENT`, violating the namei assertion at `sys/kern/vfs_lookup.c:518`.
   The captured backtrace points to generic path lookup reached through the
   io_uring front end. This is a kernel crash, not an unsupported-opcode skip.
2. **Nonseekable I/O:** `pipe-eof`, `eventfd`, `shutdown`, buffer-ring cases,
   `msg-ring-fd`, `resize-rings`, and several linked/restriction cases report
   `-ESPIPE` (`-29`). Investigate shared read/write offset handling before treating
   each affected test as an independent bug.
3. **Cancellation and completion ordering:** failures in `io-cancel`,
   `sync-cancel`, `skip-cqe`, disabled-ring polling, and eventfd disable behavior.
   SQPOLL socket cases also report `-EAGAIN` where the tests expect completion.
4. **Other observable contracts:** closing a ring via a close request,
   invalid-address rename errno, file-registration limit negotiation, and
   deferred-taskrun shutdown behavior differ from the Linux run.
5. **Timeouts and cleanup:** six upstream cases timed out at 45 seconds, and the
   extended native soak timed out at 300 seconds. Preserve these as unresolved
   results rather than passes. The follow-up log records longer retries.

Some failures are expected consequences of missing capabilities: `link` and
`msg-ring` include polling-ring setup, which the candidate rejects. Other
failures involve test prerequisites: the initial `poll-mshot-update` run exhausted
`kern.ipc.maxpipekva`. The follow-up VM sets that boot tunable to 256 MiB and
uses 150-second per-case limits for registration, read/write, timeout, and
multishot-poll update. All four focus cases still timed out at 150 seconds despite the larger pipe cap.
See the exact retry outcomes in the JSON and retry log.
`connect` skips on the candidate after reporting no support, but passes on Linux;
that skip is not counted as successful compatibility.

## Application checks

Fio uses `ioengine=io_uring`, 4 KiB blocks, depth 16, and a 16 MiB regular file.
It writes CRC32C-tagged blocks and reads them back with fatal verification errors
enabled. Buffered, direct, registered files/buffers, and SQPOLL all pass on both
VMs. The same checks pass in a separate fresh candidate VM. These establish a
real application path through io_uring; Bun, Node/libuv, and database adoption
have not been qualified by these fio runs.

## Hardware measurements

These are **initial measurements of the installed September 24 kernel**, not the
newer candidate. The machine is an Intel i7-12700H with 20 visible CPUs and about
32 GiB RAM, WITNESS enabled, and concurrent VM/build activity. The regular-file
workload is small and warm-cache; it does not measure sustained device throughput.
There is no native-Linux hardware comparison.

Each row is the median of three runs: 64 MiB file, 4 KiB random I/O, 70% reads,
30% writes, one-second ramp and three-second measurement. Latencies below include
submission time; completion-only latency would understate inline completion cost.

| Mode | IOPS | Read p99 (µs) | Write p99 (µs) |
|---|---:|---:|---:|
| psync, depth 1 | 58,815 | 13.50 | 44.29 |
| io_uring, depth 1 | 53,876 | 19.07 | 53.50 |
| io_uring, depth 8 | 66,695 | 292.86 | 309.25 |
| io_uring, depth 32 | 50,535 | 1,417.22 | 1,466.37 |
| SQPOLL + registered files, depth 32 | 161,309 | 428.03 | 460.80 |

The higher SQPOLL throughput comes with busy polling: fio reports about 99.5%
userspace CPU in that mode; its per-process CPU numbers do not include all kernel
worker/poller cost. Depth histograms, CPU figures, exact commands, limits, and
submission-counter deltas are retained in the hardware JSON. psync's squeue
submission delta is zero; every timed io_uring job has a positive delta.

An earlier hardware attempt using registered buffers failed at depth 32 because
128 KiB of buffers exceeded the account's 64 KiB memlock limit. The final hardware
workload uses registered files without fixed buffers. Candidate-VM fixed-buffer
verification still passes. Diagnostic attempts remain in the evidence directory.
