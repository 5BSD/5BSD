# Packages and Ports

5BSD is pkgbase-native: the base system is installed and upgraded as pkg(8) packages, never as distribution tarballs, and every capability bundle under `/Capabilities` is a package too. There is no public 5BSD package service. Base packages are built from the source tree and served from a repository on local disk; third-party software comes from the FreeBSD ports repositories unchanged, because the ABI 5BSD reports is FreeBSD's. This chapter explains the package catalogue, the local repository model, the upgrade loop, and how a bundle travels through pkg into a running unit.

## Naming and sets

`PKG_NAME_PREFIX` is `5BSD` (`share/mk/bsd.pkg.pre.mk`, `Makefile.inc1`), so every base package is `5BSD-<name>`: `5BSD-runtime`, `5BSD-clibs`, `5BSD-kernel-generic`, `5BSD-switchboard`. The version string carries the `5BSD` brand from `sys/conf/newvers.sh`. The maintainer and WWW fields point at the 5BSD repository. Sub-packages follow FreeBSD's scheme (`-dev`, `-man`, `-dbg`, `-lib`); there is no `-lib32` because `LIB32` is a broken option.

Metapackage sets are generated by `release/packages/create-sets.sh` from the `PKG_SETS` annotations of the packages already built, so the prefix is carried through automatically:

| Set | Contents |
|---|---|
| `5BSD-set-base` | everything a running system needs |
| `5BSD-set-base-jail` | the same for a jail root |
| `5BSD-set-minimal`, `5BSD-set-minimal-jail` | packages tagged `PKG_SETS= minimal` (runtime, switchboard, capsule and friends) |
| `5BSD-set-kernels` | the kernel packages; `5BSD-kernel-generic` is the 5BSD kernel |
| `5BSD-set-tests` | the 46 `*-tests` packages |
| `*-dbg` variants | debug symbols for each set |

`5BSD-pkg-bootstrap` replaces the ports `pkg` in images.

## Where a file's package is decided

A file belongs to the package named by `PACKAGE=` in the Makefile that installs it, or by a `tags=package=` entry in the mtree files. `packages/<name>/Makefile` declares the package's sets, dependencies and UCL manifests; `release/packages/ucl/<name>.ucl` applies to that package and `<name>-all.ucl` to all its sub-packages (`release/packages/ucl/README` states the dependency policy: do not add a dependency on `rc`, `devd` or `cron` merely because a package ships a script for them). Kernel modules with `PACKAGE=` in their module Makefile travel with that package rather than with the kernel, through `KMODTAGS` in `sys/conf/kmod.mk`.

What lives in `runtime` versus its own package is a deliberate split:

| Own package | Contents |
|---|---|
| `capsule`, `capsulectl`, `switchboard`, `switchboardctl`, `sysextctl` | PID 1, the service manager and their tools |
| `bsdaudit`, `bsdauth`, `bsdcrypto`, `bsddevice`, `bsdlog`, `bsdnetwork`, `bsdnotify`, `bsdtrace-provider`, `bluetooth` | providers with their `.cap` bundles (`bsdtrace-provider` is the BSDTrace daemon, distinct from the `bsdtrace` Intel PT tool) |
| `libservice`, `libcapbundle`, `libcapsulert`, `libcapreclaim`, `libcapability`, `libchannel`, `libshmring`, `libcryptodesc`, `lib*cmp`, `libnotify` | the plane's libraries |
| `oes`, `mac-abac`, `hwtlm`, `bsdinstruments`, `bsdtrace` | security and observability tools |
| `runtime` | BSDFilesystem, BSDPower, BSDTime, BSDExtension, BSDNamespace and BSDVM, plus anoint(1) and reclaimstat(8): the providers a system cannot boot or reclaim without |

`packages/runtime/runtime.ucl` declares the `capability` user and group and carries pre- and post-install scripts that create uid and gid 976 on an upgraded root and bootstrap `pwd.db` on a fresh one. `packages/switchboard/switchboard.ucl`'s post-install removes retired bundle trees that would otherwise be boot-fatal, since switchboard fails closed on an invalid system bundle. The `rc` package removes a stale `rc.d/oracled`.

## The local repository model

`/etc/pkg/5BSD.conf`, installed from `usr.sbin/pkg/5BSD.conf.in`, ships disabled:

```
5BSD-base: {
  url: "file:///usr/obj/usr/src/repo/${ABI}/latest",
  enabled: no
}
```

It stays disabled until a repository exists at that path. The FreeBSD ports repositories in `/etc/pkg/FreeBSD.conf` remain enabled; only `FreeBSD-base` must be disabled so `pkg upgrade` never replaces 5BSD base packages with FreeBSD ones. `docs/pkg/5BSD.conf.sample` and `docs/pkg/FreeBSD.conf.sample` are the two override files:

```
# /usr/local/etc/pkg/repos/5BSD.conf
5BSD-base: { enabled: no }

5BSD: {
  url: "file:///usr/obj/usr/src/repo/${ABI}/latest",
  enabled: yes,
  priority: 100
}
```

```
# /usr/local/etc/pkg/repos/FreeBSD.conf
FreeBSD-base: { enabled: no }
```

`${ABI}` expands to `FreeBSD:16:amd64`; `usr.sbin/pkg/config.c` computes it from `__FreeBSD_version` and registers `OSNAME` as `FreeBSD`, which is why FreeBSD ports packages resolve. The repository may be copied to any directory on the target machine as long as the catalogue and package paths are preserved; regenerate the catalogue with `pkg repo` whenever packages are published. `pkg -vv` shows the effective configuration. An older installation that still names `pkg.5bsd.org` gets DNS errors on `pkg update`; the `5BSD-base: { enabled: no }` line is the fix.

## Building and upgrading

The loop from source to an upgraded machine, from `docs/book/src/operations/upgrading.md`:

```sh
cd /usr/src
make -j$(sysctl -n hw.ncpu) buildworld buildkernel packages \
    PKG_CMD=/usr/local/sbin/pkg-static
pkg repo /usr/obj/usr/src/repo/${ABI}/<version>
ln -snf <version> /usr/obj/usr/src/repo/${ABI}/latest
bectl create pre-upgrade
pkg update -f -r 5BSD
pkg upgrade -r 5BSD
reboot
```

`PKG_CMD=/usr/local/sbin/pkg-static` is required: the dynamic ports pkg(8) links against a libc symbol version the tree does not export and fails, while `pkg-static` is self-contained. Build the kernel before `make packages`, so the module packages match it. `pkg upgrade -r 5BSD` restricts the upgrade to the local repository: it upgrades every `5BSD-*` package to the catalogue's version, touches nothing from the ports repositories, and leaves the previous boot environment intact for `bectl activate pre-upgrade`. Applications are upgraded separately with `pkg upgrade -r FreeBSD-ports`.

Migrating a FreeBSD 16-CURRENT pkgbase system is a one-time replacement, because `FreeBSD-*` and `5BSD-*` are different package names and `pkg upgrade` cannot cross them:

```sh
bectl create pre-5bsd-migration
pkg update
pkg delete -fa
pkg install -r 5BSD 5BSD-set-base 5BSD-kernel-generic
reboot
```

After reboot, `uname -i` shows `GENERIC`, and `kldstat -v | grep mac_capability` shows the plane compiled in rather than loaded. [Building](../operations/building.md), [Installing](../operations/installing.md) and [Upgrading](../operations/upgrading.md) walk through each step with the release targets.

## The installer and media

Release media (`make -C release memstick` or `cdrom`) stage a fresh system, add the installer environment, build an offline pkgbase repository under `/usr/5bsd-packages/offline`, embed `pkg` on the media, and boot with `capability_plane="NO"` so bsdinstall runs on stock init. bsdinstall's `pkgbase` script installs from that repository with `pkg install -U -y -r 5BSD-base <packages>`; a plain pkg install is the whole step. The installer offers offline or network sources, requires ZFS for the guided install, writes the tmpfs `/Capabilities/Run` line into fstab, and runs two 5BSD-specific steps: `tzfspool` (which pool the storage plane binds to, written to `/Capabilities/Config/bsdfilesystem.ucl`) and `capabilitypolicy` (who gets admin sessions, written to `/Capabilities/Config/principal-policy.ucl`, root and wheel by default). There are no distribution sets: `NODISTSETS` is the release default.

## Bundles as packages

A capability bundle is a directory tree, `/Capabilities/System/<Name>.cap/Bundle.ucl` plus `Units/<unit>.unit/{Unit.ucl,bin,Config,lib}`, and pkg owns it like any other files. The provider's Makefile declares the directories with `DIRS` and tags each with the package name, for example in `usr.sbin/BSDNetwork/Makefile`:

```
PACKAGE=	bsdnetwork
NETWORKCMP_CAP=	/Capabilities/System/Network.cap
NETWORKCMP_CAPPACKAGE=	bsdnetwork
NETWORKCMP_CAP_UNITS=	${NETWORKCMP_CAP}/Units
NETWORKCMP_CAP_UNITSPACKAGE=	bsdnetwork
```

so the package's plist owns the bundle directories, not only the files in them. That is what makes `pkg delete` remove the whole `<Name>.cap` directory and makes an uninstall visible to switchboard.

Installation is discovery, not registration. switchboard watches its install roots (`registry_watch.c`): an edge-triggered `EVFILT_VNODE` watch on `/Capabilities/System` and `/Capabilities/Apps`, and one level below on each bundle directory, since a package manager removes a bundle's files inside its directory without touching the root. A burst of writes from `pkg add` coalesces into one event, a two-second quiescence timer (`SWITCHBOARD_REGISTRY_WATCH_SETTLE`, 1 to 60 seconds) lets the extraction finish, and then the registry is rescanned exactly as `switchboardctl reload` would: new units are loaded, removed ones unloaded, and the running-bundle markers under `/Capabilities/Run/live` republished. A bundle that fails validation is quarantined and logged rather than failing the scan (a broken system bundle, by contrast, stops switchboard from starting: system policy fails closed). An edit deep inside an installed bundle is not an install event and still needs an explicit reload.

Removal is reconcile, not reaction. When a bundle disappears, its units are unloaded and its data under `/Capabilities/Data/<bundle>` becomes an orphan; each provider's reconcile pass (libcapreclaim(3), run on a timer with a grace period and at boot) compares its durable state to the set of installed and running bundles it sees through delivered directories and reaps what no bundle claims. reclaimstat(8) shows what each provider manages. An upgrade that replaces a bundle in place restarts its units through the same watch. The one deliberate UNIX socket in switchboard exists for this path: a pkg post-deinstall script is a plain root context with no lookup channel, and the reclaim bridge lets it trigger a bundle-label reclaim. [Containers and Storage](../plane/containers-and-storage.md) describes the data layout; [Packaging and Shipping](../develop/packaging.md) shows how to build a bundle package of your own.

`switchboardctl install path.cap` verifies and copies a bundle into `/Capabilities/System` as a root-owned policy tree for the case where no package exists, and `switchboardctl verify` validates a bundle's structure, manifests, executables and dependency graph before it is packaged. `switchboardctl bundles` lists what is installed; `switchboardctl enable` and `disable` keep a bundle on disk but out of the registry.

## Ports

Ports and their binary packages are FreeBSD's. `pkg install` from the `FreeBSD-ports` repository works because the ABI matches; a port that builds on FreeBSD 16-CURRENT amd64 builds on 5BSD, with two caveats. There is no 32-bit compatibility, so a port that needs `lib32` or an i386 build fails, and a port that installs a kernel module builds it against 5BSD headers, so the KPI changes listed in [The BSD Side](bsd-side.md) apply. A port's rc.d script under `/usr/local/etc/rc.d` is run by `/etc/rc` as on FreeBSD and can be adopted by switchboard by name in `rc_adopt.conf` (see [rc and service(8)](rc-and-service.md)).

## Integrity

Packages are not signed. `release/packages/base-integrity.sh create|check|veriexec <root> <manifest>` produces an mtree baseline of an installed root, checks a root against it, and exports a mac_veriexec manifest from it; the plane's design assumes veriexec will enforce in production, but it is not loaded on the test rigs and the export is unsigned. Treat the local repository as trusted input.

## Status

All of the above is committed on `dev` and exercised: `make packages` builds cleanly with the static pkg, the installer's twenty ATF cases pass, and install and remove through a real package built with `pkg-static create` (plist owning the bundle directories, `pkg add` through the watch to a running unit, `pkg delete` through the watch to reclaim) is VM-proven. Daemons in `runtime` have no package of their own; splitting them out is future work.
