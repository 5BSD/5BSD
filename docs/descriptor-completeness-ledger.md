# Descriptor completeness ledger

This ledger is the authoritative, regenerable list of every place the kernel
reaches past `struct fileops` to a vnode, classified with the disposition that
stage 0 of the DescriptorQueue design (`docs/book/src/capability/descriptor-queue.md`,
sections 4.1, 6, 6.1.1, 6.2-6.2.3 and 6.3) gives it. Every row was verified by
reading the code at the cited line; the ledger, not the design chapter, is the
count of record. This is the end-of-stage-0 regeneration (6.3): the first
ledger was written at `46b84718217` before any of the stage-0 series landed;
the second at `1f8c7358a4d` with all of it in (`90663f0e0c0`); this one is
re-run at HEAD after the five commits that followed the series review
(`3cbf72440bd` observers' vnode hold, `dbe69afe001` displaced image state,
`80f7f749378` lock-taking flags and the fdescfs drop rule, `f134444e4b1` the
last type tests), which converted every category-A row the previous ledger
left open; and it is re-run once more at `a4bfad81171`, the quality pass that
presents stage 0 as one subsystem (D83, D84: `pipeops` on `vn_*_opt`, the
`O_PATH` tests on `f_flag`, the `copy_file_range` probe gone, `fo_setattr`
the whole `vattr` through `file_setattr_direct`, the DTrace probes), which
changes no classification.

Markers after the line number:

- ⁽ᵀ⁾ — the line is an `f_type` test against `DTYPE_VNODE` or `DTYPE_FIFO`
  (the 37 + 6 above).
- ⁽ᴺ⁾ — the code already tolerates a NULL vnode pointer (`f_vnode`,
  `p_textvp` or `imgp->vp`) by an explicit NULL check on that line or on the
  assigned alias in the next statement, or copies the pointer without
  dereferencing it. Callers of `getvnode()`, `getvnode_path()` and `fgetvp*()`
  inherit the helpers' `EINVAL` for a NULL `f_vnode` but are not marked; the
  helpers themselves are. A consumer whose callee rejects NULL (`vn_fullpath*`
  returns `EINVAL`) is not marked either; its row says "tolerates NULL" and
  how.

Categories:

- **A fileop** — the syscall or kernel path must call a `struct fileops` member.
  A row whose site was converted reads "done (`fo_X`, commit)": the hit
  survives because it is now inside the moved vnode body `vn_X`, or is a
  comment recording the preserved errno. A row left reads "deferred" (by
  decision, cited) or "keep". No row reads "open" any more: the ten hits the
  `1f8c7358a4d` ledger left open were converted by `80f7f749378` and
  `f134444e4b1` and the hits are gone; their closing dispositions are
  recorded in the list after the table.
- **B resolution** — obtains a start vnode for a lookup from a dirfd, cwd or
  root, or compares a looked-up vnode with an fd's vnode. The disposition names
  the choke point (`namei_setup`, `namei_handle_root`, `fgetvp_lookup`,
  `cache_fplookup_dirfd`), "compare by object id", or "ENOTDIR for non-vnode".
  All of it is stage 1.
- **C exec** — image/text related. After `1f8c7358a4d` the exec core reaches
  the image only through `imgp->is_ops` (`struct image_source_ops`, 6.2.3), so
  the dispositions are: "construction site" (the three entry forms in
  `do_execve`), "vnode backend, by design" (every row of
  `kern/exec_image_vnode.c`, naming the `is_*` op the line implements),
  "p_image consumer" for `p_textvp` readers (citing the fallback commit
  `7b587d57f55` where one was added, or saying how the code tolerates NULL),
  and the veriexec/authority rows that work on a vnode by design (D28: a
  served image is denied under enforcement; the explicit denial is stage 3).
  The two "→ P_KPROC" rows of the previous ledger are gone (`e9ce901379b`).
- **D vm** — VM object, sendfile, mmap.
- **E vfs-internal** — legitimately vnode-only; disposition "keep".
- **F observer** — reporting, audit and MAC paths that switch on `f_type`.
- **G driver** — code outside the core that needs a real vnode.

## Fileops tables

One row per `struct fileops` definition in the tree, found by

```sh
cd /usr/src/sys && git grep -n -E '^(static )?(const )?struct fileops .* = \{' -- .
```

(35 tables, `vn_openfileops[6]` among them) plus five tables the pattern
misses because they are built from a macro or filled at run time from a copy
of `vnops` (`lease_control_ops`, `lease_owner_ops`, `pfs_snapshotops`,
`tmpfs_fnops`, `zfshandle_anon_dir_ops`): 40 rows, the same 40 as at
`46b84718217`; no table was added or removed by stage 0. Each table's members
were read at HEAD; "carries `f_vnode`" is what `finit_open`/`vn_open` or the
table's own constructor stores there. The eleven columns are the stage-0
members in the order `fo_pathconf`, `fo_statfs`, `fo_fsync`, `fo_setattr`,
`fo_fadvise`, `fo_readdir`, `fo_copy_file_range`, `fo_acl`, `fo_extattr`,
`fo_fcntl`, `fo_advlock`, and say what each table **actually installs** now:

- `vn` — the moved vnode body `vn_*(fp)` installed directly (both devfs
  tables; `path_fileops` for its seven; `pipeops` for `fo_advlock` through
  `pipe_advlock`, see `vn/pipe`);
- `vn/opt` — `vn_*_opt`, which runs `vn_*` when `f_vnode != NULL` and
  `invfo_*` otherwise: the three *sometimes-vnode* tables, FIFOs and
  anonymous pipes (`pipeops`, since `a4bfad81171`, D83), pseudo-terminal
  masters (`/dev/ptmx` carries the vnode, `posix_openpt(2)` does not) and
  linuxkpi files (devfs open carries it, `fd_install()` does not), D72. These
  are the only members anywhere that inspect `f_vnode`;
- `vn/pipe` — `pipeops`'s two own answers, `pipe_pathconf` (`PIPE_BUF` for
  `_PC_PIPE_BUF` else `EINVAL`; a FIFO's other names go to its vnode) and
  `pipe_advlock`; until `a4bfad81171` the six vnode-answered members were
  `pipe_*` copies branching on `PIPE_TYPE_NAMED`, now `vn/opt`. `pipe_advlock` admits
  `F_FLOCK` only: a FIFO takes `flock(2)` through `vn_advlock`, an anonymous
  pipe answers it with its own `EOPNOTSUPP`, and both give `fcntl(2)` record
  locks and the close-time unlock `invfo_advlock`'s `EBADF` (D72, D73, D81);
- `own` — the table's own implementation (`vnops`, `vn_openfileops` and the
  three run-time copies: `vn_openfile_*` wrappers around the `vn_*` bodies,
  or the body itself for `fo_fsync`, `fo_readdir`, `fo_copy_file_range`,
  `fo_advlock`; `socketops`: `soo_pathconf`, `PIPE_BUF`/`EINVAL`;
  `path_fileops`: `path_advlock` (`kern_descrip.c:6223`, `80f7f749378`),
  which answers only the close-time `F_UNLCK` of POSIX locks through
  `vn_advlock` so closing an `O_PATH` descriptor releases the process's record
  locks on the file as any close does, and is `invfo_advlock` for every other
  request; `flock(2)` and the `fcntl(2)` lock commands never reach it because
  the table carries neither `DFLAG_FLOCK` nor `DFLAG_RECLOCK`);
- `inv` — the member is NULL and the `fo_*` dispatcher in `sys/file.h` calls
  `invfo_*`, which returns the errno the removed type test gave that system
  call: `pathconf` `EOPNOTSUPP`; `fadvise` `ENODEV`; `fcntl` `EBADF`;
  `advlock` `EBADF` (`flock(2)` never reaches it, refusing a table without
  `DFLAG_FLOCK` first; D73, D81); `statfs`, `fsync`, `setattr`, `readdir`,
  `copy_file_range`, `acl`, `extattr` `EINVAL`;
- `bad` — `badfo_*` (`EBADF`). No table installs a `badfo_*` for any of the
  eleven: `badfileops` leaves them NULL (so they would dispatch to `invfo_*`),
  which is unreachable because `fget()` refuses a `badfileops` file first.

Several system calls keep a probe ahead of the table, where the type test
stood, so the dispatch is not the first refusal and the probe is as
side-effect free as the type test was:

- the `fcntl(2)` record-lock cases (`F_GETLK`, `F_SETLK`, `F_SETLKW`,
  `F_SETLK_REMOTE` and the `F_OFD_*` forms) probe the **flags**, not the
  member: `(fo_flags & DFLAG_RECLOCK) == 0 → EBADF` (`kern_descrip.c:810`,
  `:946`; `80f7f749378`, D74/D79) before the `struct flock` is copied in or
  validated and before `P_ADVLOCK`, `FHASLOCK` or `FHASOFDLOCK` are touched;
- `flock(2)` probes `(fo_flags & DFLAG_FLOCK) == 0 → EOPNOTSUPP`
  (`kern_descrip.c:4546`) before its `how` argument is validated, so a kqueue
  or socket gets `EOPNOTSUPP` for any argument and `flock(pipe, 0)` is
  `EBADF`, the argument check (the anonymous pipe shares the FIFO table and
  passes the flag probe);
- when the table then answers `EOPNOTSUPP` — an anonymous pipe through
  `pipe_advlock`, or a filesystem without `VFCF_OFDLOCKS` for an OFD lock —
  the `FHASLOCK` (`:4580`) or `FHASOFDLOCK` (`:898`) flag set ahead of the
  request is cleared again, since no lock can be held;
- `closef`/`fdclearlocks` still probe the member (`fo_advlock == NULL` →
  skip, `:3042`, `:3384`, D73); `path_fileops` now has one, so the close-time
  POSIX unlock runs for an `O_PATH` close again (finding 8);
- `copy_file_range(2)` no longer probes (`a4bfad81171`, D83): the input table
  answers, `vn_copy_range` refuses a partner without a vnode and
  `invfo_copy_file_range` gives `EINVAL`, both where the vnode test stood;
- `fdesc_setattr` probes `fo_setattr == NULL` (`fdesc_vnops.c:629`, D29) for
  the old drop rule and otherwise makes one `fo_setattr` call (D84), see below;
  the Linux fileattr calls probe `fo_setattr == NULL` (`linux_file.c:525`) and
  return the fileop's answer unmapped (D82), the Linux `FS_IOC_SETFLAGS`
  ioctl probes it for `ENOTTY` (`linux_ioctl.c:4045`), Linux `getdents`
  probes `fo_readdir == NULL` for `EINVAL` (`linux_file.c:782`) and Linux
  `F_SET_RW_HINT` probes `fo_fcntl == NULL` for `EINVAL` before the `copyin`
  (`:2347`), all as `getvnode()` answered (`f134444e4b1`).

`posix_fadvise(2)` refuses a non-`DFLAG_SEEKABLE` table with `ESPIPE` before
dispatching, so `fo_fadvise` is never reached on `pipeops`, `ptsdev_ops`,
`linuxfileops` or `path_fileops`. The `fsync`, `fchflags`, `futimes`/`futimens`,
ACL set/delete and `F_READAHEAD` system calls still refuse `path_fileops` with
`EBADF` ahead of the table (D71). `fchflags(2)` refuses `VNOVAL` once the
descriptor is known, so `(badfd, -1)` is `EBADF` and every open descriptor
gets `EOPNOTSUPP` (`f134444e4b1`, D81; a type without attributes once answered
`EINVAL` to that value).

The fdescfs rule (`80f7f749378`, D81): `fdesc_setattr` forwards `va_size`
to `fo_truncate`, `va_mode` to `fo_chmod`, `va_uid`/`va_gid` to `fo_chown`
and only what those did not take — times, flags, `va_vaflags` — to
`fo_setattr`, and only if there is any; each fileop's answer stands. A table
with no `fo_setattr` member (sockets, kqueues, shm) has no settable
attributes and keeps the old drop rule: the change is dropped (`0`), except
that `va_flags` → `EOPNOTSUPP`. A table with the member answers for its
descriptor: an anonymous pipe or a `posix_openpt(2)` master reports `EINVAL`
for times and flags where the missing vnode once meant "dropped", `EINVAL`
for `chflags(2)` where the bridge once said `EOPNOTSUPP` (declared, D81,
D82). A FIFO carries a vnode and its `vn_*` run for every attribute; a
`/dev/ptmx` master or a devfs-opened linuxkpi file carries one too, but
their tables answer `fo_truncate`/`fo_chmod`/`fo_chown` with `invfo_*`
(`EINVAL`, as `fchmod(2)` on them always did), so only times and flags
reach the node through `vn_setattr_opt` (D82).

Three table flags say what the type does on its own; the flags column reads
`PRIVWRITE / FLOCK / RECLOCK`:

- `DFLAG_PRIVWRITE` (D65, D71; `20dbcc341de`) is carried by `vnops`, the
  `VN_OPENFILEOPS` macro (all six `vn_openfileops`), `devfs_ops_f` and
  `devfs_ops_nonpassable_f`, by the three run-time copies of `vnops` through
  the copy, and since `f134444e4b1` by `shm_ops`: a private mapping of a shm
  object is copy-on-write like a vnode's (`shm_mmap`), so a private
  `PROT_WRITE` mapping needs no `CAP_MMAP_W` there either. No other table
  carries it; `path_fileops` does not (an `O_PATH` descriptor cannot be
  mapped). `vm_mmap.c:471` keys on it and no longer tests `f_type`;
  `vm_mmap_file` keeps the `prot ⊄ maxprot` → `EACCES` refusal as the
  backstop, now reported through `EXTERROR` (`9bba5eadd58`, `f134444e4b1`,
  D74).
- `DFLAG_FLOCK` and `DFLAG_RECLOCK` (`80f7f749378`; `sys/file.h` `0x80`,
  `0x100`) say whether the type takes `flock(2)` locks and `fcntl(2)` record
  locks. `vnops`, the `VN_OPENFILEOPS` macro and the three run-time copies
  carry both, as do `devfs_ops_f` and `devfs_ops_nonpassable_f`; `pipeops`
  carries `DFLAG_FLOCK` only (a FIFO takes `flock(2)` through `vn_advlock`,
  record locks were `EBADF` for it as for a pipe); `path_fileops` carries
  neither although it installs `path_advlock`; no other table carries either.
  `flock(2)` and the record-lock commands probe these flags before argument
  validation (above), so the member's presence no longer decides admission.
