## 1. The kernel capability core

### One-paragraph summary
The kernel capability core is the trusted computing base of the 5BSD capability plane: a message-passing framework (`mac_capability`) in which every kernel service is reached through a `DTYPE_MAC_CAPABILITY` file descriptor, plus Capsicum and process-descriptor extensions that make a held descriptor, rather than uid/PID/path, the unit of authority. It exists because FreeBSD's Capsicum confines a process but gives it no capability-shaped way to obtain or delegate authority. 5BSD adds per-credential program nonces (a MAC label: inherited on fork, rotated on exec), a service registry with sync (`CALL`) and async (`SENDMSG`/`RECVMSG`) messaging, nine service modules (isolation, system gates, coalition, capprotect, node, mount, accounting, identity, channel) plus two test fixtures, and descriptor-level controls (transfer state and ceilings, one-shot exec/fork propagation, capmode-only mmap/lookup). Since 1cfe04dcaf39 the plane is compiled into every kernel (`standard` in `sys/conf/files`); `/dev/mac_capability` is claimed exclusively by capsule at boot and everyone else receives delivered descriptors or uses the ungated `mac_capability_channel_create(2)` pair syscall. The Capsicum side gained `SYF_CAPREQUIRED` (syscalls legal only inside capability mode), capability-mode exec of dynamic images (`kern.elf64.capmode_interp`), environment descriptors (`envfd`), and `CAPENABLED` marking of reboot/kld/jail/audit syscalls so born-in-capmode gate daemons can act through held claims. Kernel-facing client libraries are `libcapability` (sync wrapper), `libchannel` (async event-loop channel) and `libcapsulert` (shared wire types and claim parsers).

### Policy points
- `kern.mac_capability_isolation.enforce` (RDTUN, default 1) -> enforce or only trace resource-access denials (ownership denials always enforced) -> loader.conf.
- `kern.mac_capability_{isolation,capprotect}.max_auth` (RDTUN), `kern.mac_capability_system.max_auth` (RW) -> cap on outstanding tokens -> loader.conf/sysctl.
- `kern.mac_capability_coalition.max`, `.max_members` -> coalition limits -> sysctl.
- `kern.elf{32,64}.capmode_interp` (RWTUN, default 1) -> may a capmode process exec a dynamic image via the brand interpreter -> loader.conf/sysctl.
- `kern.envfd.max_{objects,bytes,user_objects,user_bytes,value_size}` -> envfd resource caps -> sysctl.
- Isolation claims/tokens (FI_OP_CLAIM*/MINT*/AUTHORIZE with FI_NET_{BIND,CONNECT}, FI_JAIL_{CREATE,ATTACH,SET,GET,REMOVE}, FI_VSOCK_* masks) -> who may touch a claimed vnode/endpoint/jail -> minted at runtime by capsule/switchboard from bundle claims.
- System gates (SYS_OP_CLAIM/MINT/AUTHORIZE, SYS_GATE_* mask; hooks `system_check_*`, `kld_check_*`, `kenv_check_*`, `prison_check_*`, per-OID `system_check_sysctl`) -> whether privileged ops succeed -> held claim minted by capsule.
- capprotect shields (CP_OP_SHIELD/PROTECT mask) -> debug/signal/sched/ktrace/wait/suspend/core/priv access from a foreign program -> switchboard launcher (manifest `protect`) or self.
- Nonce rotation (`vnode_execve_relabel`) -> exec is a new identity, fork shares it -> fixed kernel rule.
- Per-fd monotone state (`cap_xfer_*`, `cap_cloexec_limit`, `cap_clofork_limit`, `cap_mmap_capmode`, `cap_lookup_capmode`) -> set by the delivering process.
- `SYF_CAPREQUIRED` in syscalls.master -> capmode-only syscalls (today `pdself`) -> compile time.
- `/dev/mac_capability` (0600) exclusive claim by capsule -> only capsule connects by name; others EACCES -> boot; plane-free boot via loader `capability_plane="NO"` is handled in capsule.
- `LOCAL_CAPMODE_SERVER` / `LOCAL_CAP_CONNECT` -> require the AF_UNIX peer to be in capmode -> setsockopt.

### What the book must explain
1. The authority rule: a held capability fd (rights, ioctl allowlist, transfer ceiling) is the authority; uid/PID/path are transitional. Nonce = program identity; fork shares, exec rotates.
2. How capabilities reach a process: capsule owns `/dev/mac_capability`; switchboard delivers fds at launch; `mac_capability_channel_create(2)` gives a private lookup channel; nothing is opened by name from a sandbox.
3. CALL vs SENDMSG/RECVMSG, the credential trailer, badges, tokens, revocation, minting, and how libchannel/libcapability map onto them.
4. Isolation claims and tokens per resource class, which MACF hooks enforce them, and `enforce=0` test mode.
5. System gates and perform ops that let born-in-capmode daemons (BSDTime, BSDSysctl, BSDExtension, BSDNamespace, BSDPower) do privileged work; per-OID sysctl isolation.
6. Descriptor discipline: `cap_xfer_*`, ONCE/LOCKED exec/fork propagation, `cap_mmap_capmode`, `cap_lookup_capmode`; handing a child a descriptor it cannot leak.
7. Process descriptors as capabilities: pdself/pdcmp/pdincapmode, ambient-free pdkill/pdwait, lifecycle knotes, node SET_CRED/REAP_*, coalitions with deadlines/watchdogs/leaders.
8. capprotect shields and launcher-applied protection (manifest `protect`).
9. Capability-mode exec: `SYF_CAPREQUIRED`, `capmode_interp`, why daemons no longer appear as `ld-elf.so.1`.
10. envfd as the capmode-safe carrier for configuration values.
11. Testing on a real plane: plane-free boot, run_tests.sh, `mac_capability_versions.h`.
12. Doc drift fixed since the baseline (4b24f728d376): mac_capability_system.4 and _capprotect.4 regenerated from the code, libcapsulert.3 added, libcapability.3 covers all six functions. Still open: the capprotect proto header comment (section 14, open finding 3).

## 2. Security policy modules and MAC framework changes (non-plane)

### One-paragraph summary
Beside the mandatory mac_capability plane, 5BSD widens the TrustedBSD MAC framework itself and ships two optional, statically compiled policy modules. The framework gains 62 net-new policy entry points (65 members added to `mac_policy.h`; three replace 5BSD's early mount hooks with upstream's richer signatures) covering vsock, waspnest/vmm, ZFS administration, vnode change notification, process lifecycle, file descriptors, rctl, kld unload, setsockopt and pts; hot hooks get FPFLAG fast paths, a per-policy `mac_framework:::policy-decision` DTrace probe reports each module's verdict, and `MAC_MAX_SLOTS` rises from 4 to 7. `mac_abac` is a label-based, first-match-rule Type-Enforcement policy (labels are `key=value` sets in the `system:mac_abac` extended attribute) managed over `mac_syscall(2)` by `mac_abac_ctl(8)` and `mac_abacd(8)`. OES (OpenEndpointSecurity) is an Apple-Endpoint-Security-style AUTH/NOTIFY event framework exposed through `/dev/oes` and `liboes(3)`, with `oeslogger(8)` as the installed consumer. Both are boot-only (`MPC_LOADTIME_FLAG_NOTLATE`, no unload) and compiled into GENERIC via the new `MAC_ABAC` and `OES` options, alongside `MAC_VERIEXEC` which is now static but not enforcing. A compatibility-first HardenedBSD import adds BIND_NOW (full RELRO) by default, zeroed jail(8) allocations and three defensive fixes, with an audit ledger and fault-injection suite; the platform-hardening plan (Compatible/Protected/Locked) is design-only.

### Policy points
- `mpo_*` hooks (62 new) -> allow/deny or observe the operation -> implemented by whichever policies are loaded (mac_capability, mac_abac, OES, mac_test_hooks).
- `security.mac.mac_abac.mode` (0/1/2) -> disabled/permissive/enforcing -> sysctl, `mac_abac_ctl mode`, `mode` key in `/etc/mac_abac.conf`.
- `security.mac.mac_abac.default_policy` -> allow or deny when no rule matches -> sysctl / `mac_abac_ctl default` / config `default_policy`.
- `security.mac.mac_abac.enabled`, `.log_level`, `.locked` (RD; once locked, no rule/mode changes until reboot), `.extattr_name` (RDTUN) -> module on/off, logging verbosity, lock state, label xattr name -> sysctl / `mac_abac_ctl lock|log`.
- `mac_abac` rule table (sets 0-65535, first match; `allow|deny|transition`, subject/object patterns, `subj_ctx`/`obj_ctx`) -> per-operation decision and exec label transitions -> `/etc/mac_abac.conf` via `mac_abacd`, or `mac_abac_ctl rule ...` at runtime.
- `abac_label_check_relabel` -> credential relabel requires `PRIV_MAC_PARTITION` and may only narrow -> kernel, fixed policy.
- `security.oes.require_auth_clients` -> deny AUTH-hooked operations when no client is subscribed -> sysctl.
- `security.oes.auth_fail_closed`, `.default_deadline_ms`, `.default_deadline_miss_mode` -> outcome when an AUTH client misses its deadline or the queue is full -> sysctl defaults, overridable per client via `OES_IOC_SET_DEADLINE_*` ioctls.
- `security.oes.max_clients`, `.default_queue_size`, `.cache_max_entries`, `.default_self_mute`, `.default_muted_paths[_literal]` -> resource limits and initial noise suppression -> sysctl (`oeslogger -n` clears mutes).
- Per-client OES state (subscriptions, mutes, scope, mode, decision cache) -> which events a client sees and may veto -> ioctls / `liboes(3)`; opening `/dev/oes` needs device privilege (devfs).
- `security.mac.test_hooks.deny.<hook>` -> force-deny a hook for testing -> sysctl (test module only).
- `MAC_VERIEXEC` state -> verified execution enforcement -> `veriexec(8)` manifest load + enforcement sysctls; not entered by default.
- `BIND_NOW` src option -> eager binding/full RELRO for all built programs and libraries -> `src.conf(5)` `WITHOUT_BIND_NOW`.
- `RACCT` default-on -> makes `mac_rctl_check_*` and rctl gates effective -> GENERIC (removed `RACCT_DEFAULT_TO_DISABLED`).

## 3. The userland capability-plane runtime

### One-paragraph summary
The userland plane is the process spine that turns the kernel's mac_capability primitives into a running system: capsule is PID 1 (installed as /sbin/capsule ahead of /sbin/init via `init_path`), claims resources and system gates exclusively, shields itself with capprotect, and pdfork(2)s exactly one child, switchboard, which is the 5BSD service manager. switchboard scans capability bundles (`*.cap` with `Bundle.ucl` + `Units/<u>.unit/Unit.ucl`) under /Capabilities/System, /Capabilities/Apps and per-user /Capabilities/Users/<uid>/Agents, launches units born in capability mode with a sealed bootstrap descriptor, supervises them by process descriptor, and runs the reverse-domain naming registry over which every service is discovered and activated on demand. libservice is the SDK both sides use (provider lifecycle, consumer `service_open`, storage/namespace/extension/vsock self-service, session minting); libcapbundle parses and validates manifests and the principal policy; libcapreclaim gives providers the reconcile loop that reaps per-bundle state when a bundle is removed. Sessions are provisioned by login/su/sshd asking BSDAuth (system.Auth) to mint a scoped lookup channel from /Capabilities/Config/principal-policy.ucl, and anoint(1) replaces sudo/doas with per-command elevation. It exists so that authority is a held capability rather than uid/path/PID, and so rc(8) keeps working beside the plane.

### Policy points
- `capability_plane` loader tunable -> plane on/off at PID 1 -> loader.conf / loader prompt.
- `init_path` -> capsule first, /sbin/init fallback -> /boot/loader.conf.d/capsule-loader.conf.
- /etc/capsule.conf `integrity{ptrace,signal,sigkill,sigcont,visible,wait,sched,core,ktrace}` -> capprotect flags on PID 1 (signal/sigkill/sigcont mandatory).
- /etc/capsule.conf `claims.network[]{port,protocol,direction,domain,address}` -> exclusive endpoint claims (max 32; foreign nonces get EACCES); `claims.system[]` -> gated ops: kldload, kldunload, reboot, swapon, swapoff, sysctl, kenv, kenv_read, acct, audit, settime, jail (lib/libcapbundle/gates.h).
- capsule.conf `control_socket`/`service_manager` -> root-only control socket (SHUTDOWN/STATUS/RELOAD) and first child.
- Unit.ucl top-level keys (libcapbundle_parse.c:904): program, activation, restart, control, capabilities, user, group, stop_timeout, max_failures, arguments, environment, protect, limits, umask, level, ambient, mint_authority, watchdog, visible, domain, directories, holds.
- `activation{boot,ipc[name|{name,requires}],timer{interval},path{path},socket[{name,listen,backlog}],schedule,persistent,queue_directory,on_mount,helper}` -> when a unit launches and which names it publishes/gates.
- `restart` never/always/on-failure; `stop_timeout` 1-300; `max_failures` 1-100 -> supervision.
- `control` core/system/user -> who may stop/restart/unload (CORE: nobody).
- `visible` [user|system] -> which domain kinds may resolve the unit's names; `domain` system/user -> which names the unit itself resolves.

## 4. System capability providers (BSD* daemons), client libraries and ctl tools

### One-paragraph summary

5BSD replaces ambient root privilege for system facilities with sixteen capability providers: each is a switchboard-launched daemon exposing one well-known wire name (`system.X`), reached by a client over its per-process mac_capability lookup channel with `service_open(3)`, and answering a small typed op set defined in a protocol header. Fifteen of the sixteen are born in capability mode (the manifest `ambient` flag defaults to false in `lib/libcapbundle`, the default `user` is `capability`); the resources they need are delivered by switchboard as directory descriptors (`directories = [...]`) and privileged kernel operations run through Capsule-minted "system" gate tokens (`capabilities { system = [...] }`) instead of uid checks. Only BSDVM is still `ambient = true`. Every provider carries a per-label policy file (keyed by the caller's unforgeable manifest label, default-deny where the facility is dangerous), a `protect` shield, a USDT DTrace provider, a BSD*.8 man page, a typed client library with a .3 page, usually an operator ctl tool, and ATF tests under `usr.sbin/BSD*/tests`. Since the fork point the area adds about 65k lines across the 15 core daemons, 21k in client libraries, 4k in ctl tools and 66k in BSDBluetooth (78/62/28/68 commits).

## 5. Storage: TrustedZFS and the Filesystem capability

### One-paragraph summary

5BSD replaces ambient, name-addressed ZFS administration with a capability model in three layers. In the kernel, **TrustedZFS** adds a new file type (`DTYPE_ZFSHANDLE`) minted on `/dev/zfs`: a dataset or pool handle that pins its object by guid, carries a rights mask fixed at mint time, narrows monotonically via derive/openat, passes over channels, and drives the existing DSL paths through ~40 `ZFD_*`/`ZPD_*` ioctls, including *anonymous mounts* (a filesystem mounted outside the global namespace, reachable only through a returned dirfd). Above it, **BSDFilesystem** (wire name `system.Filesystem`, the `[TZFS]` daemon) is the born-in-capability-mode broker that owns the pool behind `/Capabilities`, derives each claimant's dataset from its unforgeable channel label, mounts stores and delivers directory descriptors, enforces quotas, offers snapshots/versions and atomic transactions, opens policy-listed paths for sandboxed units (`open_paths`), and reconciles per-bundle **containers** under `/Capabilities/Data` against the installed set. Consumers never declare storage in a manifest; they self-serve at runtime through `libservice` (`service_storage_open(3)` and friends), while `libtrustedzfs` and `libbsdfilesystem` are the lower-level client libraries and `tzfsctl(8)` is the operator probe. Around this sit new MAC hooks for ZFS (`mpo_zfs_check_*`, snapshot create/delete/revert), Capsicum-aware fd handling inside OpenZFS, a small `mac_capability_mount` kernel service for whitelisted mounts by sandboxed processes, and installer/release changes that make root-on-ZFS the required 5BSD default and wire the chosen pool into `bsdfilesystem.ucl`. The earlier "flavors" (pre-baked OS image templates) feature was built and then removed entirely (46d06d3edaf6); the installation-ledger model was likewise replaced by the container model.

### Policy points

- `mpo_zfs_check_send/receive/dataset_destroy/pool_destroy/pool_export/key_load/key_unload/key_change` (MAC hooks) -> whether a cred may perform that ZFS management op -> any loaded MAC policy (`sys/security/mac/mac_system.c`); currently only stub/test policies implement them.
- `mpo_mount_check_snapshot_create/delete/revert` -> snapshot lifecycle authorization, called from both legacy ioctls and handle verbs -> MAC policy modules.
- `ZH_*` rights mask + `ZHF_*` flags at mint (`ZFS_IOC_DATASET_OPEN`) -> which verbs a handle may ever perform; only narrowable via `ZFD_DERIVE`/`ZFD_OPENAT` -> minter (BSDFilesystem or root program), gated by existing `zfs allow`/jail visibility.
- `ZFD_LIMIT` / `tzfs_limit_*_ioctls[_by_rights]` -> per-handle ioctl op subset (Capsicum `cap_ioctls_limit` profile) -> holder, one-way.
- `vfs.zfs.trustedzfs.enum_max_entries` sysctl -> bound on kernel memory per enumeration verb -> loader/sysctl.
- `mac_capability_mount` fstype whitelist + `MOUNT_F_*` flag approval -> which mounts a sandboxed caller can request; jail `allow.mount.*` second layer -> compiled-in table + jail params.
- `/Capabilities/Config/bsdfilesystem.ucl` keys `pool`, `roots.*`, `ephemeral.sync`, `default_refquota`, `reclaim_interval` (10-86400 s, default 300), `staging_idle_grace` (1-86400 s, default 300) -> pool selection, dataset roots, per-claim refquota default, container reaping cadence, abandoned-transaction reaping -> `tzfs.conf(5)`; installer `tzfspool` sets `pool`.
- `open_paths[]` (`label`, `path`, `rights`, `prefix`) -> default-deny per-label isolated-open grants for `service_open_isolated(3)` -> same config file (base policy ships in `usr.sbin/BSDFilesystem/bsdfilesystem.ucl`).
- Channel label -> dataset namespace derivation (claims scoped to the caller's own subtree; SHARED/GROUP scope by bundle/group) -> switchboard-set label, not a wire argument.
- Unit manifest `capbundle/bsdfilesystem.ucl`: `directories = ["/dev", "/"]`, `control = "core"`, `protect = [...]`, `user = "root"` -> what the broker is handed at launch and who may manage it -> switchboard manifest.
- Compiled caps: `BSDFILESYSTEM_CONN_MAX_CLAIMS 32`, `NS_MAX_CLAIMS 64`, `MAX_SNAPSHOTS 256`, `MAX_OPEN_POLICY 32`, `MAX_WORKERS 4096`, `DESTROY_MAX_DEPTH 64` -> DoS bounds -> `usr.sbin/BSDFilesystem/bsdfilesystem.h`.

### What the book must explain

1. The handle model: a ZFS dataset/pool as an unforgeable fd with a rights mask, pinned by guid (rename-proof, ENXIO after destroy), narrowed by derive/openat, passed over channels - versus classic `zfs allow`/root.
2. Anonymous mounts: what "mounted but path-invisible" means, the anchor/registry lifetime (handles and dirfds; last anchor unmounts; provider restart is transparent), and why `procstat`/`getcwd` show no path.
3. BSDFilesystem as the storage broker: born in capability mode with delivered `/` and `/dev`, mints per-label handles, serves each client on its own channel; ZFS is required, UFS root tolerated in degraded isolated-path-only mode.
4. The container model and `/Capabilities/Data` layout (unit persistent/cache, bundle shared, `Shared/<group>`), the `Run/live` markers, and the reconcile that reaps uninstalled bundles (with the pinned-clone `EEXIST` retry rule).
5. Consumer self-service: storage is claimed at runtime with `service_storage_open(3)`, never declared in a manifest; lifetimes (persistent/cache/ephemeral) and scopes (unit/shared/group); read-only shared views and the shared environment.
6. Versions and transactions: SNAPSHOT/LIST_VERSIONS/ROLLBACK/OPEN_VERSION and TXN_BEGIN/COMMIT/ABORT semantics (staging clone, origin binding, atomic swap), plus the boot and idle reapers and their config keys - currently undocumented in the book.
7. Quotas: `default_refquota`, `STAT_CLAIM`, `SET_QUOTA`, and the compiled per-connection/namespace/snapshot caps.
8. Isolated opens: `open_paths` policy in `bsdfilesystem.ucl` as the replacement for manifest file delivery (`service_open_isolated`, `service_open_config`), default-deny and `prefix` device-family matching.
9. Operator tasks: editing `tzfs.conf(5)`, `tzfsctl ping/request/release`, the DTrace providers and shipped scripts, how the installer picks the pool (`tzfspool`) and why `/Capabilities/Run` is tmpfs.
10. The ZFS MAC hooks and Capsicum-aware embedded fds as kernel enforcement points (and that no production MAC policy yet implements the `mpo_zfs_check_*` hooks).
11. `mac_capability_mount(4)`: the whitelisted mount door for sandboxed processes and its relation to jail `allow.mount.*`.
12. Client libraries for tool authors: `libtrustedzfs` ioctl-limit profiles and `libbsdfilesystem`, and the retired concepts to avoid (flavors, installation ledger, `capabilities.open`, socket-based daemon).

## 6. Linux emulation (Linuxulator, io_uring/squeue)

### One-paragraph summary

5BSD ships the FreeBSD Linuxulator as a default-on, 64-bit-only ABI (`linux_common`/`linux64` loaded from `stand/defaults/loader.conf`, `linux_enable=YES` in `libexec/rc/rc.conf`, 32-bit module never loaded) and has grown it from ~270 functional x86_64 syscalls at baseline to 334 functional handlers covering the Linux 7.3 table (slots 0-472), with 80 `DUMMY()` stubs reduced to 36. The point is that Linux binaries are policed by MAC/capability layers *beneath* the translation boundary, so the emulator gains real semantics (pidfd, futex2, signalfd, ptrace SEIZE/LISTEN/INTERRUPT/registers, rseq, NUMA, quota, swap, perf_event, abstract AF_UNIX, AF_VSOCK, netlink SOCK_DIAG/KOBJECT_UEVENT, cgroup/cpuset procfs, FUSE lock/notify parity) without Linux's own in-kernel sandboxes. The largest single piece is a new ABI-neutral completion-ring engine, **squeue** (`sys/kern/sys_squeue.c`, 9.5k lines, native syscalls `squeue_setup/enter/register` 636-638), over which `linux_io_uring.c` is a thin Linux front end: all 65 io_uring opcodes and all 38 ordinary register commands dispatch, with unsupported items negotiated away via PROBE/`-EINVAL`/`-EOPNOTSUPP`, never silently wrong. An acceptance contract (`docs/linuxulator-implementation-gate.md`) requires every syscall/option to be qualified in disposable amd64 ZFS-root QEMU guests against a Linux 6.18/7.1 reference VM (`tools/test/linuxulator/qemu-gate.py`); ~50 `docs/linuxulator-*.md` files and 141 test programs (131 `linux_*`, 10 `squeue_*` in `tests/sys/kern/`) record the evidence. Seccomp and Landlock exist only as uncommitted working-tree files (`linux_seccomp*.c`, `linux_landlock.c`, `sys/sys/abi_sandbox.h`): in progress, not inventoried here.

### Policy points

- `compat.linux.osrelease` / `osname` / `oss_version` (per-jail params) -> advertised kernel version (default 5.15.0) -> sysctl / jail(8).
- `compat.linux.setid_allowed`, `preserve_vstatus`, `map_sched_prio`, `dummy_rlimits`, `ignore_ip_recverr`, `default_stacksize`, `default_openfiles`, `use_real_ifnames`, `emul_path`, `debug` -> behaviour knobs (documented in `linux.4`) -> sysctl/loader tunables.
- `compat.linux.aio.max_wired_pages` (new) -> legacy AIO ring wiring cap -> sysctl.
- `kern.squeue.max_workers` (1-256, default 8), `max_wired_pages` + `RLIMIT_MEMLOCK` -> io_uring/squeue worker and wired-memory ceilings -> sysctl/loader; `live_requests`, `workers`, `rings`, `submitted`, `overflowed` read-only.
- Capsicum: squeue syscalls `CAPENABLED`; ops honour target `cap_rights`; capmode rings restricted to registered files; abstract AF_UNIX names unbindable in capmode -> kernel.
- `IORING_REGISTER_RESTRICTIONS` / BPF request filters -> per-ring opcode/flag policy -> application.
- MAC hooks fire on translated native ops (no Linux-specific hooks) -> `mac_capability`/OES policy -> see security sections.
- `linux_enable`, `linux_mounts_enable` -> rc.conf; `linux_common_load`, `linux64_load` -> loader.conf.
- Privilege: `init_module`/`finit_module` EPERM, `vhangup` PRIV_TTY_STI, `ioperm/iopl` PRIV_IO only when raising, quota/swapon native priv checks.

## 7. Virtualization: waspnest (bhyve engine), vmm, VirtIO guest stack, vsock, BSDVM

### One-paragraph summary

5BSD turned FreeBSD's bhyve/vmm into a much larger virtualization program, reviewed and tracked under the working name "WASPNest". Relative to bc301fee4cb it adds ~85k lines to `usr.sbin/bhyve` (modern VirtIO 1.4 PCI transport, packed rings, multiqueue, ten new VirtIO device models, i6300esb watchdog, pvpanic, a versioned checkpoint manifest and live-migration control plane), ~72k lines to `sys/amd64/vmm` + `sys/dev/vmm` (~40k of it Intel nested VMX; the rest a kernel-owned INIT/SIPI startup transaction, dirty-page logging, snapshot envelopes, pvclock, MTRR/CPUID modelling), ~17k lines of guest-side VirtIO drivers (nine new plus modern-transport work in the existing ones), an `AF_VSOCK` socket domain with guest transport and host device model, a read-only `virtiofsd(8)`/`mount_virtiofs(8)` pair, MAC hooks gating VM lifecycle and vsock provider attachment, and a capability-plane broker `BSDVM` (`system.VM`) that hands vsock endpoints to sandboxed units. Two naming facts matter: at HEAD the hypervisor binary is still `bhyve` (the `waspnest` symlink was promoted to primary on 2026-09-05 and reverted the same day; the Makefile now says "bhyve ... keeps its name"), and "waspnest" survives only as the qualification-package/docs name; the VM daemon is `BSDVM`. Nearly everything is model-tested and committed; the ledgers say live guest qualification, nested VMX exposure, and production live migration remain open.

## 8. Bluetooth (BLE host, Mesh, virtual HCI)

### One-paragraph summary
5BSD replaces FreeBSD's BR/EDR-only userland Bluetooth story with a full Bluetooth Low Energy host and a Bluetooth Mesh stack, built in userland over a heavily extended netgraph kernel layer. The kernel side (`ng_hci`, `ng_l2cap`, `ng_btsocket`, `ng_ubt`) gains Bluetooth 5.2-era LE support: 36 LE meta-events, extended/periodic advertising, PHY/data-length/privacy commands, LE credit-based and Enhanced Credit-Based (ECBFC) L2CAP channels, connection-parameter update, a new `BLUETOOTH_PROTO_ISO` SEQPACKET socket family for CIS/BIS isochronous streams, and `ng_hci_virt(4)`, a hardware-free virtual controller with a `/dev/vhciN` userspace bridge. On top sit two daemons: `BSDBluetooth` (source still calls it `blued`; wire name `system.Bluetooth`), a from-scratch ATT/GATT/SMP/EATT/HOGP/ISO host daemon that is the sole radio owner and is shipped as a capability bundle (`/Capabilities/System/Bluetooth.cap`), and `meshd`, a Mesh Protocol 1.1 node/provisioner built on the pure `libblemesh` library that reaches the radio only through BSDBluetooth's control socket. `libble(3)` (161 functions) is the client API, `bluedctl(8)` (83 verbs) and `meshctl(8)` (23 verbs) are the operator CLIs, and `vhcitool(8)` drives the virtual controller for CI. HOGP reports are injected through the new `vhid(4)` virtual HID transport so `hkbd`/`hms`/`hmt` attach natively. The whole thing was built and reviewed by repeated adversarial/spec-conformance passes (~160 ATF programs, 23 libFuzzer harnesses, spec-derived oracle generators) and is extensively documented as "not yet released; IPC and persistence formats unstable". The "skyblue" rename recorded in memory was abandoned: commit dfa22c054dd4 purged it and nothing in HEAD uses that name.

## 9. Observability

### One-paragraph summary

5BSD's observability story ("ObservableBSD") layers three things on FreeBSD's DTrace. First, instrumentation: the kernel gains roughly 65 new SDT providers and ~577 new probe definitions (Capsicum, jail/jaildesc, cred/priv, fd, mqueue/aio/squeue, tty, vsock, trustedzfs, the ten `mac_capability*` providers, OES, ABAC, virtio, Bluetooth...), and 64 userland USDT providers are added to security-relevant base programs (capsule, switchboard, every BSD* daemon and client library, libcasper and all its services, every PAM module, login/su/cron/inetd/syslogd/devd, jail). The design doc's phrase is "everything is traced". Second, tooling: a C port of the ObservableBSD suite — `bsdinstruments` (240-profile DTrace catalog with OTLP export), `hwtlm` (hardware telemetry), `bsdtrace` (Intel PT execution tracing over the hwt(4) framework), a shared `libotelexport`, and 87 ready-made scripts in `/usr/share/dtrace`. Third, authorization: `BSDTrace` publishes `system.Trace` and delegates rights-limited DTrace consumer descriptors to allow-listed labels, backed by a new capability-safe `dtrace_fdopen(3)` in libdtrace, so tracing no longer requires opening `/dev/dtrace` as root. The unified logging substrate (`BSDLog`/`system.Log`, `liblogcmp`, `logctl`) is the diagnostic-telemetry counterpart and itself exposes DTrace probes; BSM audit stays the security trail.

## 10. Cryptography and networking

### One-paragraph summary
5BSD replaces "open /dev/crypto and hold the key bytes" and "open a socket wherever you like" with two brokered, capability-shaped services. On the crypto side the kernel gains a new descriptor type, `DTYPE_CRYPTO`: a passable, rights-masked handle on one OpenCrypto session whose key material is generated inside the kernel and never leaves it; on top of it sit kernel-resident named (volatile) keys, HKDF child derivation, X25519/Ed25519, TTL expiry, irreversible attenuation, revocation and a kqueue filter. `BSDCrypto` (wire name `system.Crypto`) is the born-in-capability-mode broker that mints those descriptors under a fixed algorithm-profile policy, and `libcryptocmp` is the consumer API. On the network side `BSDNetwork` (`system.Network`) is an outbound connection broker: a client asks for RESOLVE/CONNECT/UDP/LISTEN and receives a real, rights-narrowed socket over SCM_RIGHTS, gated by a per-label UCL policy with an SSRF guard; a one-point kernel fix lets capability-mode processes reach INET bind/connect at all. The Linuxulator wave adds NETLINK_SOCK_DIAG, uevent netlink, Linux abstract UNIX-socket names, multicast source filters and unidirectional pipes. sshd now mints each session's ambient lookup channel through the `system.Auth` agent over a per-connection channel instead of a control socket, and every PAM module carries USDT DTrace probes. Everything here is committed on `dev`.

### Policy points
- BSDCrypto profile policy -> which cipher/MAC/keylen/IV/tag/rights combinations may be minted, TTL bound, name charset -> compiled in `usr.sbin/BSDCrypto/policy.c` (not a config file).
- `CRYPTOCMP_GENERATE_F_NIST_APPROVED_ONLY` -> restricts a request to AES-CBC/GCM + HMAC-SHA2 -> per-request flag from the client.
- Owner scoping of named keys -> owner = caller's channel label, never wire-supplied -> enforced in BSDCrypto worker + kernel `cd_owner`.
- `kern.crypto.cryptokey_max_objects`, `cryptokey_max_owner_objects` -> global / per-owner named-key caps -> sysctl.
- PRIV_DRIVER snapshot at `/dev/crypto` open -> who may create named keys -> kernel cryptodev; BSDCrypto opens as root then `NOPRIVS`.
- `cd_rights` restrict/revoke -> monotonic attenuation on a descriptor -> `CIOCSCRYPTODESCRIGHTS`/`CIOCCRYPTODESCREVOKE`.
- BSDCrypto manifest -> boot activation, `protect`, delivered `directories` (/dev, /Capabilities/*), limits, umask -> `usr.sbin/BSDCrypto/capbundle/crypto.ucl`.
- `CRYPTO_RECLAIM_INTERVAL` -> reclaim sweep cadence -> environment of the unit.
- BSDNetwork per-label policy -> resolve/connect/udp/inet4/inet6/internal booleans per client label, fail-soft to compiled default; admin-right sessions bypass -> `$CAPABILITY_UNIT_DIR/bsdnetwork.conf` (UCL).
- `internal = false` -> SSRF guard: loopback/link-local/RFC1918/ULA denied by default -> same file.
- LISTEN -> loopback-only OS-assigned port, requires label `listen` policy -> BSDNetwork.
- BSDNetwork manifest -> `user = "capability"`, protect list, limits -> `capbundle/bsdnetwork.ucl`.
- `LOCAL_CAP_CONNECT` / `LOCAL_CAPMODE_SERVER` / `LOCAL_CAP_REQ` -> require peer/self capability mode on a UNIX socket -> `setsockopt(SOL_LOCAL)`.
- `CAP_XFER_ONCE/NONE` transfer state -> whether a received fd may be re-sent -> `cap_xfer_limit(2)`, checked in `unp_internalize`.
- `mac_vnode_check_uipc_bind/connect`, `mac_file_check_receive`, `mac_pipe_check_read/write`, `mac_file_check_ioctl` -> MAC veto on UNIX bind/connect, fd receive, pipe I/O, ioctl -> MAC policies (mac_capability).
- sshd mint lock `/var/run/sshd.mint.lock` -> serialises session minting across monitors -> fixed path.
- veriexec manifest parser -> rejects malformed hashes -> `sbin/veriexec`.

### What the book must explain
1. The `DTYPE_CRYPTO` model: keys are born in the kernel, a descriptor is the only handle, rights only shrink, and close/revoke/expire destroys the session -- and why this is not a KeyVault.
2. How a component gets crypto: link `libcryptocmp`, lazy `service_connect` to `system.Crypto`, GENERATE/GENERATE_KEY/DIGEST/RANDOM, and what the returned fd can and cannot do.
3. Named keys: owner = channel label, generation numbers, lease/rotate/delete/stat/list, volatility, reclaim on bundle removal, and `EVFILT_CRYPTODESC` for rotation/revocation notices.
4. BSDCrypto's profile policy and the NIST-approved-only flag, stated exactly as `crypto-compliance-readiness.md` does (readiness controls, not FIPS/HIPAA claims).
5. `system.Network` as an outbound broker: RESOLVE/CONNECT/UDP/LISTEN, what rights the delivered socket has, that the broker never proxies data, and the HELLO version handshake.
6. Writing `bsdnetwork.conf`: default vs per-label blocks, the six booleans, the `internal` SSRF guard, fail-soft semantics, admin bypass.
7. Why capmode INET bind/connect needed `bindat/connectat` with a real fd, and how the resolver works without Casper (files via BSDFilesystem).
8. UNIX-socket capability semantics: SCM_RIGHTS attenuation and transfer limits, `LOCAL_CAP_*`/`SO_PEERCAPMODE`, and the MAC bind/connect/receive hooks.
9. How an ssh login obtains its ambient lookup channel (listener -> per-connection channel -> monitor mint via `system.Auth`), and the `SERVICE_LOOKUP_FD` contract sessions inherit.
10. Linux compatibility networking additions (sock_diag, uevent, abstract names, multicast filters, unidirectional pipes) as a short reference, pointing to `docs/linuxulator-*.md`.
11. Observability: USDT providers in BSDCrypto, BSDNetwork, libnetworkcmp and every PAM module; OpenBSM audit of session/resolve decisions.
12. Gaps to flag: `libcryptodesc.3` exists since 4b24f728d376, but `cryptodesc_named_list()` loses entries when `max` < CRYPTODESC_NAMED_LIST_MAX (section 14, open finding 4); asymmetric RSA/ECDSA and certificate validation remain design-only.

## 11. Build, packaging, installation, release and boot

### One-paragraph summary

This area is everything between `git clone` and a booted 5BSD machine: the build knobs, the pkgbase package catalogue, the release media, the installer, the boot loader and the first-boot defaults. 5BSD is pkgbase-native (`PKG_NAME_PREFIX=5BSD`, ~75 new `packages/*` dirs, 46 of them test packages), 64-bit only (LIB32 broken, i386/armv7 dropped from the universe), and root-on-ZFS by default because the storage plane (BSDFilesystem, `/Capabilities`) needs a pool at first boot. GENERIC *is* the 5BSD kernel: the capability plane is compiled in as `standard`, OES/MAC_ABAC/veriexec/cryptodev/vsock are static, `COMPAT_FREEBSD32` is removed. The loader boots `/sbin/capsule` first via `init_path`, and `capability_plane="NO"` hands PID 1 to stock init for recovery, tests and the installer media. `bsdinstall` was re-cut around ZFS+pkgbase, an offline on-media repo, the `capability` uid/gid 976 identity, a tmpfs `/Capabilities/Run`, and two new steps (`tzfspool`, `capabilitypolicy`). There is no public package service: base updates come from a locally built `file://` repo, ports packages from FreeBSD. Everything here is committed on `dev`; the stale VBSD kernel name, the inert loader module preloads and the installer's call into a removed `switchboardctl` verb were all fixed in b56526805a0a.

### Policy points

- `capability_plane` (loader tunable) -> capsule hands PID 1 to `/sbin/init`, plane never starts -> `/boot/loader.conf`, set by release media.
- `init_path` (loader) -> PID 1 candidate order, capsule first -> `stand/defaults/loader.conf`.
- `/Capabilities/Config/principal-policy.ucl` (`admin { uids; groups }`) -> who gets SYSTEM sessions -> written by `bsdinstall capabilitypolicy` / `BSDINSTALL_CAPABILITY_ADMIN_*`.
- `/Capabilities/Config/bsdfilesystem.ucl` `pool=` -> pool the storage plane binds to -> `bsdinstall tzfspool` from `ZFSBOOT_POOL_NAME`.
- `/usr/local/etc/pkg/repos/5BSD.conf` + `/etc/pkg/5BSD.conf` -> where base updates come from (disabled until local repo exists).
- `NOPKGBASE`, `NODISTSETS`, `PKGBASE_PKG_PACKAGE[_SHA256]`, `PKG_CMD` -> media composition and pkg provenance -> `release/Makefile`.
- `VMFS`/`VMFSLIST`, `IMAGE_HOSTNAME` -> image root filesystem and hostname -> `release/Makefile.vm`, `vmimage.subr`.
- `WITH_/WITHOUT_BIND_NOW`, `BHYVE_SNAPSHOT`, `LIB32` (broken) -> hardening and 64-bit-only stance -> `src.conf`.
- `KMODTAGS`/`PACKAGE=` in module Makefiles -> which pkgbase package a `.ko` ships in.
- `zfs_enable`, `auditd_enable`, `linux_enable`, `mac_abacd_enable`, `blued_enable`, `meshd_enable` -> rc.conf.
- `boot_policy=strict` in `/efi/5bsd/loader.env` -> loader never falls back to a foreign boot pool on install media.
- `write_installer_fstab` -> tmpfs `/Capabilities/Run`, `/tmp`, `/var` on read-only media; zfsboot adds the same `/Capabilities/Run` line on installed systems.

## 12. Test infrastructure and developer tooling

### One-paragraph summary
5BSD adds roughly 6,600 files of tests and developer tooling on top of FreeBSD's ATF/Kyua framework (bc301fee4cb..HEAD; ~470 commits touch these paths). The bulk by file count (5,646 under `tests/usr.sbin`) is one thing: the Bluetooth stack suite plus its libFuzzer seed corpus. The rest splits into four layers that the tree's own docs insist must not be confused: (1) ordinary Kyua suites that run in-session or on any installed host (component libraries, control tools, parsers, device-model harnesses compiled against real sources with mocks); (2) suites that need a booted VM with the capability plane **off** so a test can claim `/dev/mac_capability` itself (mac_capability, zfshandle, raw provider transports); (3) suites that need a live plane (capsule/switchboard integration, anointment scenarios, container proofs); and (4) QEMU/bhyve "gates" where the host only builds artifacts and a disposable guest is the sole source of evidence (Linuxulator, OES, mac_abac, TrustedZFS, WASPNest). Every daemon and library ships a `*-tests` pkgbase package (47 of them) with `atf`/`kyua` dependencies. The docs record explicit testing mandates ("do NOT skimp", "a skipped privileged test is not a pass", "QEMU is the correctness gate") and traceability ledgers (TSV) that map requirements to tests. Book coverage today is essentially nil: one sentence in the Bluetooth chapter.

## 13. Changes to the pre-existing FreeBSD base (kernel and userland)

### One-paragraph summary

This area covers everything 5BSD changed in FreeBSD files that already existed at bc301fee4cb and that no other section owns: the generic kernel (VFS, descriptors, process, jail, VM), non-virtio filesystems and drivers, arch code, libc/libsys, and classic userland tools. Four intents dominate. Linux-emulation support landed in native subsystems (OFD locks, inotify path identity, per-open FUSE handles, pseudofs thread/fd nodes, abstract unix sockets, uevent netlink, swap priority, futex_waitv, ptrace SEIZE/EXIT). Capability-plane plumbing added descriptor transfer attenuation, `pdself`/`pdcmp`, `*_gated()` kernel entry points that replace `priv_check` with a held capability, ambient lookup-channel hygiene in login/su/cron/atrun/sshd, and `shutdown`/`reboot` delegating to `capsulectl`. Hardening added 44 MAC hooks at syscall entry, `BIND_NOW` by default, jail `recallocarray`, HardenedBSD driver fixes and kinfo_proc address hiding. A single DTrace commit (`ec932ce37c73`) instrumented ~250 files without behavior change. Branding and the 64-bit-only policy (`nooptions COMPAT_FREEBSD32`, `LIB32` off) round it out. A developer porting to 5BSD notices new syscalls and constants, a few errno changes, and several kernel KPI breaks.

### Open findings

New tree problems the follow-up fixes surfaced; each verified against HEAD. All six were fixed the same day.

1. FIXED in 013a04c13274: usr.sbin/bluetooth/BSDBluetooth/blued.c (managed-launch block at the top of main, guarded by `SERVICE_BOOTSTRAP_FD`) calls `service_capability_open(ctx, "storage:state", "directory", &persist_dirfd)` and `err(1, "acquire persistent storage")` on failure, but blued.ucl declares no storage block (only `directories`, `control`, `protect`, `activation.ipc`), and `service_capability_open()` fails with ENOENT for an undeclared name. Under switchboard the daemon therefore exits at startup instead of degrading; the rest of blued already treats `persist_dirfd < 0` as "no persistence" (bond DB, resolving-list save/load), so the fail-soft path exists and the err(1) violates the no-hard-dependency rule. Fix: fall through with `persist_dirfd = -1` (log once) or add the storage claim the daemon actually wants.
2. FIXED in f578a3fa0916: the daemon side is now the bsdtrace-provider package (daemon, bundle, tracectl, bsdtrace-provider-tests); bsdtrace stays the Intel PT tool. Original finding: The retired `traced` package name survives: usr.sbin/tracectl/Makefile says `PACKAGE= traced`, release/packages/ucl/traced-all.ucl and traced-tests-all.ucl still exist ("Capability-mode TraceCmp provider"), packages/traced and packages/traced-tests still exist, and etc/mtree/BSD.tests.dist keeps a `traced` tests directory. Meanwhile usr.sbin/BSDTrace/Makefile sets `PACKAGE= bsdtrace`, which is the Intel PT execution-tracing tool's package (release/packages/ucl/bsdtrace-all.ucl: "Hardware-assisted execution tracing"), so the daemon and the unrelated tool share one package while its ctl tool sits in another. Needs a deliberate package name for the BSDTrace provider (and its tests) and the ucl/mtree/packages entries moved with it.
3. FIXED in edf6967eeff2: sys/dev/mac_capability/mac_capability_capprotect_proto.h (header comment, lines 28-31) says flags are set once per fd, protection is refcounted per flag and closing a shield fd removes only the flags it added; mac_capability_capprotect.c implements a per-process shield keyed by PID with a unique lifetime generation (`struct shield_entry`, `se_generation`, dropped at process exit before PID reuse; tokens name a shield incarnation). The comment describes the retired per-fd model that 244b0b955e11 replaced and contradicts the regenerated mac_capability_capprotect.4. Fix the comment.
4. FIXED in 013a04c13274: lib/libcryptodesc/cryptodesc.c `cryptodesc_named_list()` issues one CIOCGCRYPTONAMEDLIST that fills up to CRYPTODESC_NAMED_LIST_MAX (16) entries and returns the kernel's `cd_next_cursor`, then clamps `copied` to the caller's `max`. When `max` < 16 the entries `max..cd_count-1` of that page are discarded but `*next_cursor` already points past them, so a caller paging with a small buffer silently skips keys (the same pattern is in `cryptodesc_owner_list()`). Fix: reject `max` < CRYPTODESC_NAMED_LIST_MAX, or keep a cursor that resumes inside the page, and say so in libcryptodesc.3.
5. FIXED in edf6967eeff2: component(7) says registrations stay staged until the provider has exposed its complete `activation.ipc` set, entered capability mode and completed `service_ready`, and that "the entire endpoint set then becomes visible atomically"; libservice(3) says client demand activates each name separately, the activation callback runs per name without forcing the provider's other names to initialize, and queued clients are released only after successful per-name activation. lib/libservice/libservice.c and lib/libcapsulert/switchboard_svc_proto.h confirm the per-name model: SVC_OP_READY is an advisory (switchboard promotes to RUNNING only after independently observing NOTE_CAPMODE and all `provides` names claimed), and "per-name publication remains demand-driven after both gates" (`service_listener_activate_locked()`, ACTIVATE_NAME/NAME_RESULT). So the readiness gate is process-wide but publication is per name and on demand; component(7)'s "atomically" overstates it and should say the names become connectable together but each is published only when its activation succeeds.
6. FIXED in edf6967eeff2: share/man/man4/mac_capability_mount.4 still tells users to add `mac_capability_mount_load="YES"` to loader.conf although mac_capability_mount.c is `standard` in sys/conf/files (b56526805a0a fixed mac_capability(4) and loader.conf but not this page).
